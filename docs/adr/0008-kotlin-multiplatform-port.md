# ADR-0008 — Kotlin Multiplatform port

**Status:** Proposed
**Date:** 2026-08-07

## Context

Passweird is a CLI that only runs where Python does. The goal is a native app — starting with
Android — covering the same functionality. Kotlin is the target language.

The thing that makes this port unusual is that Passweird has **no state to migrate and no API to
keep compatible** — it has something stricter. Every output is a pure function of the user's
inputs, so a second implementation is only useful if it reproduces the first one **bit for bit,
forever**. A password that is "almost right" is simply a wrong password, and the user finds out
when they are locked out of an account, not when the code is written.

That reframes the whole exercise: this is not a port, it is a **second implementation of a
specification that was never written down**. The specification currently exists only as Python
source.

### Concrete divergence hazards, measured

These were verified against the current implementation, not assumed:

**1. Signed bytes — hits the most-used feature.** `generate_password_hkdf` (crypto.py:183) does
`charset[b % len(charset)]`, iterating bytes as `0..255`. On the JVM, `Byte` is `-128..127` and
`%` preserves the sign, so a naive port produces negative indices. Same inputs, side by side:

```
Python : Lx_uhnx0wGceDhwO98
JVM     : m=Vuh$=B-G24Dh-O9J
```

Roughly half the bytes in any derivation exceed 127, so about half the characters change. The
danger is that the wrong output **still looks like a valid password** — it passes any smoke test
that does not compare against a known-good value.

**2. ASN.1 string type in certificates.** `cryptography` encodes the certificate CN as
`UTF8String` (tag `0x0C`); BouncyCastle's `X500NameBuilder` picks `PrintableString` (`0x13`) when
the characters allow. Different DER → different signature → a completely different certificate,
even with an identical private key.

**3. `export_pgp_key_armored` shells out to the `gpg` binary** (crypto.py:638). There is no such
binary on Android. The armor format itself is simple (base64 + CRC-24 + headers), but this is a
reimplementation, not a port.

**4. FIDO2 is desktop-shaped.** `_connect_fido2_client` (crypto.py:658) uses `fido2.hid`, which
assumes USB enumeration. Android exposes its own FIDO2/CTAP APIs; this is another rewrite.

`wipe_string_from_ram` (crypto.py:21) has no JVM equivalent and is already dead code — Java
`String` is immutable and the GC relocates it, so the technique cannot be reproduced. Secrets
should be held in `CharArray`/`ByteArray` and zeroed explicitly instead.

## Decision

### Kotlin Multiplatform, with a shared deterministic core

The derivation core is **~715 lines of pure, side-effect-free mathematics**, and the part the
v1 scope needs is far smaller (see below). That profile is exactly what KMP shares well: write
and validate the critical code once in `commonMain`, run it on Android and Desktop, keep iOS
open for later.

`commonMain` has no cryptographic primitives. Since Android and Desktop are both JVM, a single
JVM `actual` (`java.security.MessageDigest`, `javax.crypto.Mac`) covers both, behind an `expect`
declaration for SHA-256, SHA-512 and HMAC-SHA512. Only an eventual iOS target would need a second
`actual`.

The CLI (`main.py`, 689 lines of argparse) is **not ported**. It is replaced by Compose UI; none
of it is reusable, and none of it needs to be.

### Python stays normative

The Python implementation remains the reference. Every change to a derivation lands there first,
regenerates the vectors below, and the Kotlin implementation must satisfy them before CI passes.
This is what makes the port maintainable rather than a slow-motion divergence.

### Golden vectors are the load-bearing mechanism

Two implementations of a deterministic generator must stay identical **permanently**, not just at
launch. Every future change — ADR-0004's HKDF domain separation is the precedent, it altered
every `info` string — must land in both at once, or the same user gets different passwords on
phone and desktop.

Hoping the two agree is not a strategy. The mechanism is a committed vector file:

```
tests/vectors/derivation-v1.json
```

generated by a Python script, consumed by **both** test suites. Each case records not only the
final output but the **intermediate values** (`master_hash`, `app_hash`, raw HKDF bytes), so a
Kotlin failure localizes to the exact stage instead of reporting "password differs".

Coverage must include the cases that actually bite:

- bytes above 127 (the signed-byte trap) — unavoidable, they appear in ~50% of positions;
- the **compliance loop firing**: measured on a sample of five contexts at length 8, the nonce
  advanced to 1 and 2 — this is a live branch, not a theoretical one;
- `length` at the boundaries (8, and 6 for the digits-only case);
- every character-class combination, since the charset is built by concatenation
  (`lowers + uppers + digits + specials`) and **any reordering changes every password**;
- empty vs non-empty temporal salt;
- non-ASCII master passwords and contexts (UTF-8 encoding must match);
- Base32 for TOTP: 20 bytes → 32 characters, **no `=` padding**.

Without this file, this ADR's recommendation would be to not port at all.

### v1 scope: passwords + TOTP

This validates the entire architecture — derivation, vectors, cross-implementation CI — against
the dominant use case, at low risk. It requires only **eight functions** from `crypto.py`:

`modified_hash`, `blend_secondary_factor`, `hkdf_expand`, `generate_password_hkdf`,
`generate_password`, `generate_deterministic_totp_secret`, `summarize_hash`,
`summarize_password_hash`.

None of them needs BouncyCastle, an external binary, or a platform API. SSH/SSL/RSA/PGP/FIDO2
follow afterwards, each landing on a base already proven correct.

## Consequences

**The hard part is small.** The must-be-exact surface for v1 is eight pure functions. That is the
single best fact in this analysis.

**The permanent cost is discipline, not code.** From the first Kotlin release onward, every
derivation change costs two implementations and a vector regeneration. The vectors make the cost
*visible and enforced* rather than optional.

**Platform boundaries that are rewrites, not ports:**

| Concern | Python today | Kotlin/Android |
|---|---|---|
| State directory | `~/.passweird` | app-private storage; log key belongs in the Keystore |
| i18n | 551 lines of dict literals in `storage.py` | Android string resources — data, mechanical |
| CLI | 689 lines of argparse | Compose UI, full rewrite |
| Secret hygiene | `wipe_string_from_ram` (dead) | `CharArray`/`ByteArray` zeroed; `FLAG_SECURE`; clipboard expiry |

**Mobile raises a threat the CLI never had.** A phone is lost and stolen far more often than a
workstation, and it holds the master password in an input field. `FLAG_SECURE` against
screenshots, biometric gating, and a clipboard that clears itself are not polish — on this
platform they are part of the threat model, and they have no counterpart in the Python version.

## Rejected alternatives

- **Android-only Kotlin.** Smaller and faster to ship, but a future Kotlin desktop would duplicate
  the core, making it *three* implementations to keep bit-identical. The core is small enough that
  sharing it costs almost nothing now and saves that outcome.
- **Kotlin/JVM replacing Python.** Removes the dual-maintenance problem entirely, but discards a
  tested, documented, published implementation, and drops the CLI — which is the tool's natural
  form for its current audience.
- **Embedding Python on Android (Chaquopy).** Guarantees identical output by construction, which
  is genuinely tempting given everything above. Rejected because it ships a Python runtime inside
  the APK, weighs tens of megabytes, and makes the security-critical code harder to audit on the
  platform where auditability matters most.
- **Deriving the vectors from the Kotlin side.** Would invert the normative relationship and let
  a Kotlin bug become the specification.
